# Hermes 就活・企業詳細リデザイン 実装仕様

更新：2026-09-14 / 仕様 v1.0 / 対象：既存の企業詳細フロー

## 0. この依頼で変えること

企業詳細を「マイページ / メール / 対策 / 管理」の4タブに再構成する。タブタップと左右スワイプで切り替える。マイページ由来の情報とメールは混在させない。目的は、募集・締切の確認から企業対策へ迷わず進めること。見栄えだけでなく、取得状態・情報の出所・操作結果が正しく分かることを完成条件とする。

**最新の変更方針：ES設問の自動取得は行わない。取得対象は募集・案内・締切。**

「ES提出の案内や締切を表示しない」という意味ではない。原文に存在するES提出期限・提出案内は募集情報として表示してよい。既存のES下書き・手入力設問・相談機能は削除しない。更新、画面表示、タブ変更、再接続、バックグラウンド処理のいずれからも、停止した設問自動取得を勝手に再開しない。

### このパッケージの役割

- `CODEX_BRIEF.md`：要求・情報設計・実装境界の正本。
- `ui_spec.json`：画面、デザイントークン、状態モデル、判定条件の構造化仕様。
- `prototype.html`：タブ・スワイプ・通常/異常状態・詳細・下書きの操作参考。ブラウザで単独動作する。
- `ACCEPTANCE.md`：項目別の検収条件。合格の証拠を提示すること。
- `screens/`：HTML試作をブラウザで実描画した画面。生成画像より優先する。
- `REVIEW.md`：この納品時点で行った試作の検証と未検証事項。

画像とHTMLは参考実装であり、本番データの正本ではない。仕様にない機能を画像から想像して追加しない。試作中の日時・件数・メール・接続状態・志望度はデモ。実在企業の最新情報として移植しない。

## 1. まず調べること。推測でファイル名やAPIを決めない

今回確認できたGitHub側の基盤は `msidragonsasus/hermes-mobile` の `dev`。確認時のツリーSHAは `fd485a69990b358f81d8dd4c12c761e7d2555d24`。同リポジトリの `DESIGN.md` はKotlin/ComposeのHermesホストUIの設計を記述する。ただし、**スクショの就活Appsの最新実装・実行環境と同一であることは未確認**。このSHAに巻き戻したり、上流リポジトリを別途作り直したりしない。

ローカル作業対象を正として、最初に次を確認する。

1. 適用範囲内の `AGENTS.md`、既存の `DESIGN.md`、作業ブランチ、未コミット差分。
2. スクショに対応する実装。`企業詳細`、`企業メール`、`保存情報を再読込`、`AXOL` などから描画元・ルート・呼び出し元を追う。表示文字列だけでなくAPI呼び出しまで確認する。
3. 企業詳細がネイティブCompose、WebView内Web UI、サーバー配信UIのどれなのか。ホストがComposeという理由だけで決めない。
4. 企業ID・募集ID・メールID・アカウントID・出典IDの対応、取得/表示APIの責務、キャッシュ、既存の下書き保存とChat遷移。
5. マイページ取得が本当に募集・案内・締切に切り替わっているか。ES設問の旧導線・旧定期処理・互換処理が残っていないか。
6. メール接続エラーの実体。スクショの「安全な保存先とログイン状態を確認」から認証切れと断定しない。エラーコードと失敗箇所を確認する。

調査結果は短い `IMPLEMENTATION_PLAN.md` に記録する。対象ファイル、利用できるAPI、不足項目、互換性、実装順、検証方法を具体化する。読めば解決できる事項はユーザーに聞かない。判明しない重要な権限・対象・不可逆な変更だけをまとめて質問する。秘密値の提示は求めない。

既存の安全性・認証・文字コードのルールは維持する。見た目の旧ルールが今回のユーザー要求と衝突する場合は、**企業詳細の範囲だけの明示的な差分**として整理する。ルートのAGENTS.mdやDESIGN.mdを丸ごと上書きしない。全機能向けに今回の長文指示を常時読み込ませる構成も作らない。

## 2. 情報設計

### 共通シェル

上から、戻る導線、企業名、少量の企業属性、固定タブ、選択タブの本文。アプリ全体のToday/Chat/Activity/Appsは既存のナビゲーションを維持する。企業タブとグローバルナビゲーションを混同しない。

企業名は1か所。不要な「企業詳細」という大見出しを重ねない。属性はインターン種別、本人の志望度、本人の選考状況など最大3つを目安にする。長い企業名は必要に応じて2行以上に伸ばし、読めなくなるほど縮小しない。未設定属性は無理に表示しない。

タブ名と順序は **マイページ → メール → 対策 → 管理**。通常文字サイズでは4つを1行で表示し、選択タブを文字・下線・アクセシビリティ状態で表す。文字拡大で収まらない場合のみタブ列を横スクロール可能にし、ラベルを切らない。

余分な「概要」「全部」「AIまとめ」「ダッシュボード」タブは作らない。4つ目の管理は、現在の情報画面を占有している接続・ID・ルール・履歴を退避するために置く。独立した第5の選考タブは今回追加しない。

### A. マイページ

**質問：この企業が案内している募集は何か。いつまでに何を確認する必要があるか。**

表示順：最終確認と更新 → 募集・締切 → お知らせ → 終了した募集への控えめな導線。

受付中の募集は、募集名・状態・期限を中心にする。主ボタンは「募集の詳細を見る」。募集の詳細内に開催日・条件・原文・取得元・確認日時・マイページへのリンクを配置する。原文にない条件は埋めない。期限不明なら「締切 未確認」。時刻不明なら日付のみ＋「時刻未確認」。勝手に23:59にしない。

複数募集は独立した行/カードにする。閉じていない確定期限を近い順、その後に期限未確認を置く。同一募集に応募、テスト、アンケート等の複数期限がある場合、種類と募集IDを保持して詳細で区別する。別募集の期限を混ぜて最短1件だけを代表表示しない。表示する期限の種類を「応募締切」等で明示する。

「受付中」と「本人が応募済み」は別の状態。募集の取得、メールの受信、下書き作成、AIの推測から応募済み・提出済み・受験済みを確定しない。

お知らせは短い一覧。見出し原則2行以内、日付、必要なら短い要点。全文は詳細へ。募集カードと同一内容の案内は募集に関連づけて重複を抑える。お知らせの既読/確認状態がないなら作り物の未読数を付けない。

同一案内を取得した回数だけ「案内の原文」カードが増える構成を廃止する。元データは削除せず、最新の案内を1件表示し、取得履歴・差分へ折りたたむ。原文自体へのアクセスは残す。

この画面には、企業メールの本文、ログインID、パスワード未登録の大カード、送信元登録フォーム、ES設問取得ボタン、技術ログを置かない。

### B. メール

**質問：この企業から届いた連絡は何か。原文を読めるか。**

表示順：最終確認と更新/必要なエラー → 検索 → すべて/未読 → 新着順の一覧。

一覧の基本単位は既存のメールID。スレッド表示を既に採用している場合は既存単位を尊重し、件数の単位を明示する。送信元表示名と受信日時、件名最大2行、本文プレビュー最大1行。通常サイズでは100〜120dp程度を目安とし、長文本文は一覧に流し込まない。文字拡大時は高さを固定しない。

タップで本文を読む。詳細に送信元アドレス、受信日時、接続アカウント、本文、元メールへの導線を置く。「このメールについて相談」はメール詳細の副次導線としてよい。AI要約を受信メール本文と同じ見た目で混ぜない。

Gmail読み取り専用を維持する。Gmail由来の未読状態を表示する場合、アプリで開いたからといって既読化しない。アプリ内確認状態を別に持つなら「未確認」等の別ラベルにし、Gmailの未読と混同しない。

検索0件と取得成功0件は別。フィルターで見つからない場合は「条件に合うメールはありません」＋条件解除。取得範囲・送信元ルールの対象で本当に0件だった場合だけ、確認範囲つきの0件を表示する。全履歴を未取得なのに「メールがありません」と言い切らない。

送信元は既存の安全なルールを利用する。`mail.axol.jp` 等の共通ドメイン全体を1社に割り当てない。アカウントID＋メッセージIDで一意性を保ち、他企業・他アカウントのメールが混入しないよう検証する。候補提案はしてよいが、曖昧な分類の自動確定は今回のUI改修で追加しない。

送信元登録フォーム、OAuth説明、仕分け中などの内部用語、保存先の技術情報は管理へ。ただし利用不能や鮮度に関わる重要な状態はメールタブでも表示する。管理に隠して正常に見せない。

### C. 対策

**質問：この企業について何を考え、何を準備し、どこから続きを始めるか。**

表示順：企業に紐づく相談を始める/続ける → 対象の募集 → 保存済み下書き → 企業研究・面接準備。

既存の企業別Chat/セッションを再利用する。企業の説明を毎回やり直させない。既存機能がある場合、モデル選択も既存Chatの選択UIを使い、固定の架空モデル名を置かない。対策タブを開いただけでLLM呼び出し・再生成を始めない。

企業ID、任意の募集ID、選択したメール/案内の参照ID、既存下書き/相談セッションIDを引き継ぐ。情報の参照範囲が分かるようにする。ログインID・資格情報・関係ない企業メールをコンテキストに混ぜない。ページ上の企業名だけ表示して、裏では全体Chatに無指定で飛ばす実装は不可。

志望動機、企業研究メモ、面接/逆質問等は保存内容に基づく入口。存在しない下書きや「完了75%」などの架空スコアは作らない。未作成なら「未作成」「相談して整理する」の自然な状態にする。巨大な質問フォームを先に埋めさせない。

事実、本人の経験、AIの提案/仮説、未確認事項を区別する。出典がある企業情報は参照を残す。元の案内が更新された場合も、下書きや本人の文章を黙って書き換えない。

ESの自動設問取得は復活させないが、本人が任意で設問を入力してES対策を行うことは妨げない。下書きの編集・保存・再開は維持する。企業への応募・提出は自動実行しない。

### D. 管理

**質問：企業の状態や情報源をどう確認・変更するか。**

「企業の管理」：本人が設定した志望度・選考状況。全社共通の固定ステージを強制せず既存データに合わせる。

「情報源と接続」：採用マイページのURL/接続状態、必要時に確認できるログインID、Gmail接続アカウント/閲覧権限、送信元ルール。ログインIDは重複表示しない。初期表示は必要最小限にし、パスワードやトークンは表示しない。

「取得と記録」：手動/自動取得の設定、最終成功/最終試行、エラーの詳細、取得履歴、案内の過去スナップショット。

未実装の自動取得スイッチを外見だけ置かない。停止中の自動取得を勝手に有効化しない。設定変更は既存のAPIと権限の範囲だけ。危険な削除・認証方式の変更・外部送信には既存の確認手続きを残す。

## 3. 操作・ナビゲーションの契約

タブタップと左右スワイプは同じ選択状態を更新する。タブは本文と一緒に流れて消えない。横スワイプで別企業やグローバルのTodayへ移動しない。最初/最後のタブで循環しない。視覚インジケーターと実際のページが常に一致する。

タブごとの縦スクロール位置、メール検索語・フィルター、対象募集、編集中の内容を保持する。企業が変わった場合は企業IDをキーに分離する。画面回転/プロセス再生成に耐える範囲は既存状態保存の仕組みに合わせて実装する。企業Aの位置や下書きが企業Bに漏れない。

戻るは、開いている詳細/シートを閉じる → 企業詳細 → 元の企業一覧という階層を優先する。タブを見た履歴を延々と逆走させない。詳細から戻ったとき、元のタブ・行付近へ戻す。

Androidの戻るエッジジェスチャーを横スワイプが奪わない。斜め/縦スクロールを誤認しない。文字選択・入力・メール本文内の操作と競合させない。メール行の横スワイプアクションは今回追加せず、タブ切り替えに意味を統一する。

画面初回表示は、既存キャッシュを先に表示する。必要な取得は既存の許可・鮮度ルールに従う。タブの作成/再描画/切替を取得トリガーにしない。連続更新は多重実行しない。更新操作は対象ソースに限定し、ES設問取得やLLMを連動させない。

「更新」は1種類の分かる操作にする。「更新」「取得」「再読込」を同じ場所に並べない。実際のAPIが保存データの再読込だけなら「最新のマイページを確認した」と表示しない。ジョブの受付と成功も区別する。鮮度はサーバーが確認した成功日時で、ボタンを押した端末時刻にしない。

## 4. 状態モデル：不具合をデザインで隠さない

データの有無、接続状態、同期状態、鮮度は別軸で保持する。全てを1つの「接続中」や成功/失敗フラグに潰さない。`data = null` と `data = []` を区別する。

| 状態 | ユーザー表示 | 維持すること |
|---|---|---|
| 未接続 | 接続が必要、管理への導線 | 0件と表示しない |
| 初回取得前 | まだ取得していない、取得する | 件数は未知 |
| 初回取得中 | スケルトン/取得中 | 空状態を一瞬表示しない |
| 成功・対象0件 | 確認範囲で0件、最終成功日時 | 未取得・検索0件と別 |
| 取得済み・更新中 | キャッシュ＋控えめな進捗 | 内容を空にしない |
| 取得失敗・キャッシュあり | 更新失敗＋前回データ＋再試行 | 最新と偽らない |
| 取得失敗・キャッシュなし | 取得失敗、件数不明＋再試行 | `0` に置き換えない |
| 再認証が必要 | 対象情報源の接続確認 | エラー原因を確認できた場合のみ |
| オフライン | 保存済み表示、必要な制約 | 下書き閲覧を妨げない |
| 一部取得 | 取得分のみ、全件未確認 | 全件取得済みにしない |
| 自動取得停止 | 停止中＋手動更新可否 | 未接続・故障と混同しない |

エラーメッセージは「何が起きたか」「今見えているデータは何か」「次に何ができるか」を短く表示する。判別できる原因の例は認証期限切れ、ネットワーク失敗、アクセス拒否、レート制限、解析失敗、サーバーの安全な保存処理の失敗。コードを確認できない場合は汎用エラーに留め、ログインし直せば直ると断定しない。

例：「メールを更新できませんでした。9/13 18:20に取得した情報を表示しています。［再試行］［接続を確認］」。技術詳細は管理に置くが、エラー自体は当該タブに残す。

ブラウザ表示で空配列だったという理由だけで、本番サービスに対象情報が存在しないとは判断しない。取得範囲・途中失敗・権限不足・ページングの有無も確認する。

## 5. 表示データの整合性

表示用に必要な概念を `ui_spec.json` に定義した。新しいDBをゼロから作る指示ではない。既存データに不足する場合は、まずアダプターで扱えるかを調べ、破壊的変更を避ける。

必須の分離は企業、募集、案内、メール、出典、本人の対策ノート、取得状態。各情報源について掲載/更新日時と取得日時を混同しない。時間は元情報のタイムゾーンを保持して表示する。日本の募集はJSTを基本表示にするが、未知のタイムゾーンや時刻を勝手に補わない。ISOの内部時刻文字列をそのまま主画面に出さない。

重複判定は可能なら情報源の安定IDを優先する。ない場合はURL・企業/募集の識別・正規化内容などで慎重に判断する。取得日時だけの変化は新規案内扱いしない。一方で、本当に期限や案内内容が変わった場合は履歴を残す。違う募集をタイトル一致だけで統合しない。正規化で重要な数値や日時を消さない。

データはソースの種類を保持する。マイページタブの表示条件はsourceType=MYPAGE、メールタブはsourceType=EMAIL等の実装上保証できる条件とする。タイトル文字列で推測してフィルターしない。

## 6. 見た目の仕様

ライト基準・ダーク対応。白い参考スクショから採用するのは企業内タブと情報分類であり、巨大な本文カードや縦に長すぎる表示は踏襲しない。

基本は明るい無彩色背景、濃い文字、深いティールの操作色。ダークは同じ階層構造にする。背景を白くするだけの修正や、全体を派手なグラデーションにする修正は禁止。既存アプリのテーマ設定を無視してライトに強制しない。色は既存のMaterial colorScheme等へ意味的にマッピングし、原則としてハードコードを画面各所へ散らさない。

余白：画面左右18〜20dp、セクション間24dp、カード内16〜18dp。角丸：主カード16dp、通常12dp、主要ボタン10〜12dp。サイズは見た目の目安で、端末・文字拡大に対応する。カードを入れ子にせず、普通の一覧は区切り線と余白で分ける。メール1通ずつを大きな灰色の箱にしない。

文字：企業名20〜22sp、重要な締切28〜32sp、募集タイトル16〜18sp、本文・メール件名15〜16sp、メタ情報12〜13sp。日本語の実描画で確認する。日時・締切の意味を小さな脚注だけに押し込めない。

1画面の通常状態で、主要な塗りボタンは原則1つ。機能すべてを同じ色・同じ大きさのボタンにしない。緊急でない通常の期限を赤くしない。エラーを弱い色にして見えなくしない。赤/黄/緑だけで状態を伝えず、短い文言と必要なアイコンを付ける。

標準のタップ領域は最低48dpを目安に確保する。小さなアイコン自体を48dpに巨大化する必要はない。本文のコントラストは4.5:1を目標にし、アクセシビリティラベル、読み上げ順、選択状態、フォーカス復帰を設定する。200%文字でも主要操作やタブ名を切らない。

マスコット、装飾イラスト、根拠のないAIスコア、意味のないグラフ、虹色のバッジ、何でもカード化、意味不明なアイコンだけの操作は追加しない。既存のアイコンセット・フォントを優先する。フォント資産をこのパッケージから取り込む必要はない。

## 7. 実装上の選択

### ネイティブComposeだった場合

既存バージョンに対応したMaterialタブとFoundationの `HorizontalPager` / `PagerState` を使う。選択状態の持ち主を1つにする。各ページは `LazyColumn` 等で縦スクロールさせ、リスト状態とキーを企業・タブごとに保持する。無限高さの縦スクロールの中に同方向リストを重ねない。既存ViewModel/Repository/Room/認証/ナビゲーションを再利用する。

既存 `HermesScaffold` が内側余白を適用しているかを確認し、二重に適用しない。Insets、IME、システムバー、グローバルナビゲーションの重なりを確認する。依存ライブラリの大規模アップグレードはこの修正に混ぜない。

### Web UIだった場合

既存のフレームワーク/ルーター/データ取得層で実装する。適切なtablist/tab/tabpanel、キーボード操作、フォーカス管理、非表示ページのinert相当、縦/横ジェスチャーの競合回避を実装する。入力中やテキスト選択中に誤移動しない。React等を別途ゼロから足さない。スタンドアロンHTMLを新アプリとして置いて実装完了にしない。

どちらの場合も、試作HTMLを単に画像にして貼る、ネイティブ画面に新設WebViewとして押し込む、既存の巨大学習/企業詳細画面にタブ見出しだけ追加する、といった近道は不可。

## 8. 範囲・安全性

今回の範囲は既存の企業詳細とそこからの詳細/対策/管理の接続。就活アプリ全体やHermes全体の作り直し、ニュース機能、選考ランキング、追加の大規模分析、モデル課金設定の刷新はしない。

Gmail/マイページの読取範囲を勝手に広げない。アカウント認証や秘密値の保存先を勝手に移行しない。メール送信・既読化・アーカイブ・削除・ラベル変更、応募/提出、Calendarへの書き込みはUI改善に紛れて実行しない。未コミット差分や既存の保存データを削除しない。テストは架空の企業・メール・IDを使い、ログやスクショに実際の秘密値を出さない。

バックエンドの改修が必要なら、UIだけの変更と分離し、理由・API差分・データ移行・権限影響を示す。UIだけで直らないメール取得障害を「画面を改善したので解決」と報告しない。依存するバックエンド不具合が残る場合は正しい失敗表示を実装し、未解決点として報告する。

## 9. 実装順・完了報告

順序：現状調査 → 変更計画 → 状態モデル/アダプター → 共通シェルと4タブ/スワイプ → マイページ・メール → 対策・管理への既存導線接続 → 異常系 → 検証 → スクショ比較 → 修正。

見た目だけを仕上げて、後から状態を適当に埋める順序にしない。正常系だけで完成扱いしない。

完了報告には、実際に変更したファイル、検収IDごとの合否と証拠、実行したコマンドと終了結果、正常4画面＋メール取得失敗のスクショ、保持した既存機能、未解決の依存、データ/権限の変更有無を含める。

ビルドできなければ、理由と実施できた範囲を記す。画像を描いただけ・ビルドだけ通った・テストを書いただけではUI/UXの完了ではない。実行していないテストをPASSと書かない。
