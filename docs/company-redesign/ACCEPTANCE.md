# 検収条件 — 本番実装用

下記はCodexが本番実装で満たす条件です。このパッケージのHTMLが動いたことと、本番アプリの合格は別です。
各項目を PASS / FAIL / 未実施 / 対象外（理由必須）で報告してください。テストコードを追加しただけではPASSにしません。

| ID | 実施内容 | 合格条件 / 証拠 |
|---|---|---|
| IA-01 | 既存の企業一覧から企業を開く | 新しい企業詳細に到達する。別途作ったモックへのリンクだけでは不可 |
| IA-02 | 4タブを順に確認 | マイページ / メール / 対策 / 管理。余計な第5タブがない |
| IA-03 | マイページとメールに異なるソースのfixtureを投入 | それぞれ対象ソースだけが表示される。タイトル依存ではなくデータで保証 |
| IA-04 | 元の企業詳細の要素を点検 | 巨大IDカード・仕分けフォーム・同一原文の大量カードが通常閲覧画面からなくなる |
| IA-05 | 募集・メール・原文を開閉 | 一覧は短く、詳細/出典は到達可能。元のタブ・位置へ戻る |
| NAV-01 | 全タブをタップ、左右にスワイプ | 両操作が同じ選択状態に反映され、インジケーターと本文が一致 |
| NAV-02 | マイページをスクロール→メール検索→別タブ→戻る | タブ別位置、検索語、フィルター、対象募集を保持 |
| NAV-03 | 縦スクロール、斜め操作、文字選択、端の戻る操作 | 意図しないタブ移動やAndroid戻るジェスチャーの妨害がない |
| NAV-04 | A社→B社、戻る、画面回転/再生成 | 企業IDで状態を分離。A社の下書き・メールがB社に混入しない |
| NAV-05 | 詳細/シートから戻る | シート→詳細→企業一覧の階層。タブ履歴を延々と戻らない |
| DATA-01 | タブ切替を10回。通信/LLMの呼び出し数を観測 | 切替そのものによる余分な取得、LLM、ES設問取得が0回 |
| DATA-02 | 連続更新・再描画・画面復帰 | リクエストの重複/競合を抑止。既存の鮮度方針と許可を維持 |
| DATA-03 | 同一案内を3回取得 | 一覧は1件。取得履歴は保存。取得時刻だけで新規扱いしない |

| DATA-05 | 似た名前の別募集に異なる締切 | 募集ごとに正しく表示。タイトル一致だけで統合しない |
| DATA-06 | 時刻不明、期限不明、複数種の期限、日時競合 | 未確認を保持。23:59等を補完しない。種類と募集IDを区別 |
| DATA-07 | 募集取得・下書き作成のみを実行 | 応募済み/提出済み/受験済みを勝手に確定しない |
| MAIL-01 | AXOL等の同一ドメインで別企業メールを投入 | 送信元ルールに従い別企業のメールを混ぜない |
| MAIL-02 | 複数アカウントのメールを投入 | accountId + messageId等で一意性・参照元を保つ |
| MAIL-03 | 未読メールを開く | 読み取り専用のまま。Gmail既読化/ラベル変更等の書込0回 |
| MAIL-04 | 未読フィルター、検索0件、全取得0件 | 意味の異なる空状態を区別。検索0件は条件解除可能 |
| ST-01 | 初回取得前・取得中 | 不明件数を0件として出さない。初回ロードで誤った空表示をしない |
| ST-02 | 取得成功・対象0件 | 最終成功と確認範囲が分かる。本当に対象0件と分かる場合だけ表示 |
| ST-03 | 更新中・キャッシュあり | 保存済み内容、スクロール、下書きが維持される |
| ST-04 | 取得失敗・キャッシュあり | 警告＋前回データ＋前回成功日時＋再試行。最新と偽らない |

| PREP-02 | 対策タブを開く/切り替える | LLMの自動実行なし。下書き等の不存在を正しく表示 |
| PREP-03 | 編集中に移動、戻る、保存、再表示 | 文章を失わない。保存済み/編集中を区別。提出と保存を混同しない |
| PREP-04 | 出典のある情報とAI提案を表示 | 事実・本人情報・仮説・未確認が区別され、参照元が追える |
| SAFE-01 | 旧ES設問取得の全入口を点検 | 表示・更新・定期処理等から無断再開しない。ES提出案内/締切と手入力下書きは残る |
| SAFE-02 | アプリの権限・外部作用を比較 | 読取範囲拡大、資格情報移行、送信/削除/応募/提出/Calendar書込を勝手に行わない |
| SAFE-03 | 既存データ・未コミット差分・設定を比較 | 破壊なし。自動取得停止設定・認証・秘密値非表示を維持 |
| UI-01 | 360/390/430dp程度の通常画面 | 主要情報・操作が読める。横はみ出しなし。普通の文字サイズで4タブが分かる |
| UI-02 | 長い社名/件名/原文、130%/200%文字 | 情報を無理に縮小しない。本文領域・詳細・主要操作を利用可能 |
| UI-03 | ライト/ダーク、各正常画面＋失敗画面 | 階層・意味・コントラストが一貫。大きな灰色カードへの逆戻りがない |
| UI-04 | TalkBack/キーボード/フォーカス/タップ領域 | 選択状態・読み上げ順が正しい。重要操作は最低48dp目安。背景にフォーカスが漏れない |
| UI-05 | スクロール、IME、システムバー、下部ナビ | 文字やボタンが隠れず、二重余白や固定要素の重なりがない |
| BUILD-01 | 既存手順でビルド・lint・対象テスト | 実行コマンド、結果、未実施理由を報告。正常4画面と失敗画面の実描画証拠を添付 |

## 最低限の受け渡しシナリオ

「A社を開く → 募集の締切確認 → 原文確認 → メールへスワイプ → 未読メールを読む → そのメールについて相談 → 企業名/募集/メール参照が引き継がれる → 下書きを保存 → 元のメール一覧へ戻る」。

別途「キャッシュがある状態でメール更新を失敗させる → 0件にならず、前回の情報を表示 → 原因に対応する復旧導線へ移動」を実施する。

## 画面比較の判断

一致させるのは情報の分離・優先度・操作の意味・余白/文字の階層であり、試作のデモ日時や架空件数ではない。プロジェクト既存のテーマとアクセシビリティ対応のために合理的な差分が出る場合は、差分と理由を記録する。
