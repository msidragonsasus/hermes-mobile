## 2. 設問の取得・保存・表示経路

1. [collection_store.py](../../server/career/career_core/collection_store.py) が対象を `nipponsteel-eng-28` / `winter-3days` として定義する。
2. [portal_reader.py](../../server/career/career_core/portal_reader.py) の `AxolReader` はAXOLの対象マイページ `com/21` をPlaywrightで読み取る。`FORM_QUESTIONS` が表示中かつ有効なテキスト・選択・ファイル入力から、field名、ラベル、形式、選択肢、maxlength、required属性を抽出する。入力値・選択済み値は読まない。
3. `questions_from_fields` が対象の25フィールドを選び、参照元設問の文脈を補い、字数を照合する。対象フィールド・依存関係はこのフォーム向けの明示定義であり、汎用のAI抽出ではない。
4. [collector.py](../../server/career/career_core/collector.py) の `update_offer` が `offers.data.questions` に保存する。設問IDは募集IDとfield名から作り、版は現在は本文と字数のハッシュ。証拠IDと取得時刻も保存する。
5. [company_views.py](../../server/career/career_core/company_views.py) の `detail` が募集と、企業に結びついた保存文書・取得根拠を返す。
6. `GET api/plugins/career/companies/{companyId}` → [CareerCompanyRepository.kt](../../app/src/main/java/com/m57/hermescontrol/career/CareerCompanyRepository.kt) → `CareerCompanyScreen`。表示時の原文処理は行頭末空白と空行の除去。第一・第二志望を書き換える処理は確認できない。

### 原文と制約について先に行う照合

- 現行DOM、抽出結果、保存questions、API出力をfield/設問IDで照合する。個人の回答値や認証情報は診断資料に入れない。過去の再取得スクリプトはDBを更新するため、読み取り調査用としてそのまま実行しない。
- 設問27・28が重複するという参照会話の主張は未確定。ラベル取得の問題、元サイトの表記、別フィールドの取り違えを区別してから修正の要否を決める。
- 表示用の短い見出し・分類は原文とは別に持つ。この1社の確認済みfieldに対する小さな対応表で足りる。未知の設問には原文由来の見出しと確認表示を使い、意味を推測して確定しない。
- 必須属性と画面上の「必須」表示の一致、改行禁止、選択肢、親子関係を照合する。現行コードの `required=e.required` だけで全必須条件を把握できたとは断定しない。
- 必須属性は必須・任意・未確認を区別する。根拠不足を任意扱いしない。年度が不明なら募集の年度を補完せず、安定した募集IDと設問IDで対応を保持する。
- 現行の設問版・文書紐付けには、全ての構造化制約が含まれていない。確認できた制約を私有データ内の設問スナップショットに追加し、その変更も検知する。旧版の設問参照は保持し、一律に上書きしない。

## 3. 最小の画面導線

### 1 — 企業詳細: 状況からESへ進む

- 先頭を企業名、対象募集、読みやすい締切、次の操作にする。締切が食い違う場合は未確定として根拠への入口を出す。
- 表示名では法人格の省略を許容するが、正式名称と企業IDは保持する。複数募集のときだけ募集選択を表示し、募集ごとの締切・設問・回答・会話を分離する。
- 主操作は状態の読込成功後に、未着手なら「ESの作成を始める」、端末下書きまたは保存済み回答があれば「ESの続きを進める」とする。未読込中は「ESの状態を確認中」、読込失敗時は再読込または確認済みキャッシュからの再開を示し、「下書きなし」に変換しない。遷移だけではAIを起動しない。
- アンケート・ES提出・SPIは各々の状況を表示する。現行取得では本人の完了を確認できないものは「未確認」。アンケートが提出条件でも、下書き作業の開始を止めない。
- 締切の元値・対象・タイムゾーンを保持し、不明なタイムゾーンを推測しない。募集全体の締切をアンケート・ES・SPIの個別締切として転記しない。現行 `deadline_from_text` もタイムゾーン不明を保持している。
- 主操作の後に最新の関連連絡・資料の要点、情報源、最終成功確認日時、原文への入口を置く。今回の取得失敗と前回の保存情報を区別し、未確認項目すべての手動チェックを利用者に要求しない。
- 全設問の原文をこの画面からES作業へ移す。企業全般の相談・面接練習は補助操作として残す。
- 「接続」は対象が分かる「案内の取得設定」へ。「企業情報を更新」と「メール・マイページを確認」の操作を区別する。

### 2 — ES作業: 回答案と残作業を見る

- 募集にひもづくES作業画面を1つ追加する。新規ナビゲーションキーはCareer内に限定する。
- 短い見出し、字数制約、本文の有無、保存状態、確認事項を1行で把握できる一覧にする。記述回答、基本情報、志向・選社軸、マイページでの対応などに整理する。全設問へ自由に移動でき、順番を強制しない。
- 行全体を操作対象にし、設問番号は補助表示にする。「原順で確認」も用意し、基本情報の候補はまとめて確認できるようにする。未確認項目を完了したように折りたたまない。
- 未取得・部分取得・取得失敗・再認証待ち・前回情報の表示を区別する。現在の対象が完全に取得できたと確認できない間は、総設問数や進捗率を確定表示しない。取得失敗を設問0件に変換しない。
- `question_refs.id` で保存文書を結び、最新の保存版と端末の未保存編集を区別する。分類不明・紐付け不明の旧文書は「関連する保存済みES」として残し、自動で別設問へ割り当てない。同じ設問に複数文書がある場合も勝手に統合しない。
- 写真・選択式を文章回答欄に変換しない。「マイページで添付／選択」と未確認の状況を示す。リンクを開いただけで完了にしない。
- 「保存情報から回答案を用意」は既存のCoachと `career_context` を使う明示操作とする。既存回答を再生成で上書きせず、不足部分を対象にする。材料が読めない場合と、読めたが不足している場合を分ける。
- 本人情報が足りないときだけ1〜2問ずつ具体的に質問する。資格・役職・志望順位を推測で埋めず、AIの判断で本人確認済みにしない。`career_context` → `select_context` で参照する材料を追い、訂正済み・古い材料が再採用されないことを確認する。

### 3 — 回答の編集・相談: 同じ設問にとどまる

- 回答を開くと企業・募集・短い設問見出し、設問原文と制約、本文入力、実測字数を表示する。
- 回答中に必須・文字数・改行禁止を確認できる位置に置き、違反理由と修正先を示す。現行のKotlinは `codePointCount`、Pythonは `len` を利用しているが、元フォームの空白・改行・絵文字等の算定と一致するかは未確認。算定差を調べ、一致が確認できない場合はその旨を表示する。コピーと版履歴の入口も残す。
- `CareerEntityDialog` の本文編集・差分表示を部品として再利用し、全文閲覧・版選択は既存の文書ダイアログから再利用する。汎用管理フォームの全項目をそのままユーザーに見せない。
- スマホでは「回答／相談」の切替とする。回答本文、相談入力、スクロール位置、対象設問を保持する。戻る先はES作業、その次が企業詳細。
- 既存 `CareerCoachPanel` と募集の会話履歴を再利用する。別のチャット基盤は作らない。
- 相談の送信時には、企業・募集・設問IDと版、文書IDと版、現在編集中の本文を固定して引き継ぐ。本文が未保存の場合も相談できる。送信後の入力変更で、受理済み依頼の対象を差し替えない。
- 現行 `CareerTarget` は既存entityの指定に限られるため、初回回答向けに検証可能な設問コンテキストを追加する。任意文字列を設問IDの代わりに扱わない。
- 他の設問の未送信相談が残っていても上書きしない。設問別に端末の入力を保持し、同じ募集の会話には対象が分かる表示を付ける。
- AIの新しい案が届いても、編集中の手入力を自動置換しない。案を見て採用・比較できるようにする。既存のAI成果保存は未確認の案として扱う。
- 「最新の保存版」と「本人が採用中の回答版」は別に参照する。本人の手動保存は採用中本文を更新し、AIが保存した新案は本人の採用操作まで候補として表示する。採用は本人確認・提出完了とは別に扱い、戻る・再読込後も同じ採用版を表示する。

### 4 — 保存: 本文・版・確認を区別する

- 本文保存は既存の `POST api/plugins/career/document`、`save_document`、版履歴、操作ID、GitHub同期を再利用する。
- 手動保存にも、募集と設問の所属、基準版、構造化制約の検証を追加する。現在、設問・字数の主な確認は `CoachTools.save` 側にあり、直接保存経路と同一ではない。必要な部分を共通化する。
- 新規文書はサーバー側でIDを採番して設問に結ぶ。既存改訂では文書の版とentityの更新版を取り違えない。
- schema 4.1の `version_evidence` 検証も維持する。既存の根拠を引き継ぎ、変更した本人主張は確認対象にする。利用者に内部の事実IDやJSONを入力させず、根拠不足を推測で補わない。
- 端末内保存、サーバー保存、GitHub同期、本人確認、企業への提出を別々に表示する。本文保存やコピーでは提出状態を変更しない。本人確認は明示操作でその版にだけ付ける。
- 原文未確認・字数超過・接続切れでも端末の編集内容は保持する。検証済みサーバー保存ができなければ、その理由と端末保存状態を表示する。確認済み保存の条件は緩めない。
- 保存ボタンを押した時点で画面を閉じない。成功応答後に版を更新し、必要なら一覧へ戻る。通信結果不明なら同一操作IDの結果を確認し、重複版を作らない。

### 5 — 再開: その回答と相談に戻る

- 既存 `CareerLocalStore` に回答の編集バッファと最後の作業位置を追加する。キーは接続先・profile・募集・設問。基準文書版と設問版も持つ。
- 端末のバッファは未保存編集の保護用に限定し、第2の正本DBにはしない。再起動後はサーバーに保存された採用版を基準にし、より新しい端末編集があれば区別して復元する。
- 入力を端末に暗号化保存し、画面離脱時にも保存を完了させる。保存に失敗した場合は「保存済み」と表示しない。
- ES作業へ戻ると、直前の設問へ進める「前回の続き」を表示する。終了・再起動後も同じ企業から再開できる。アプリ全体の起動画面ルールは変更しない。
- サーバーに新しい版があれば、端末の編集中本文を保持したまま比較する。設問削除・変更でも入力を捨てず、元の設問を参照できる状態で対応を促す。
- 再接続だけで相談送信や保存の再実行は行わない。既存の保留操作の照合・再試行を利用する。

## 4. 追加するデータ契約の範囲

既存の設問ID、文書版、企業・募集の会話、認証、操作IDを使い、次の不足だけを補う。

| 追加・拡張 | 用途・制約 |
| --- | --- |
| 設問の表示情報 | 原文とは別の見出し・分類。型・必須・改行等の制約は確認根拠付きで保持。原文を表示名で置換しない。 |
| 回答の作業状態 | 最新保存版と採用中版の参照、本人確認が必要か、原文確認が必要か、本人確認した文書版。生成状態・保存状態とは分離する。私有のCareer側データとして保存する。 |
| 相談の設問コンテキスト | 既存会話APIへ追加する任意フィールド。募集・設問・基準版・未保存本文をサーバーで検証してRunに固定する。既存クライアントの会話は維持。 |
| 端末編集バッファ | 本文、相談入力、基準版、作業位置。端末保存の成否を表示する。 |

回答一覧はまず既存の企業詳細レスポンスのquestionsとdocumentsを結合して作る。新たな全体検索APIや全社共通ワークフローエンジンは追加しない。新サーバー対応は既存capabilitiesで判定し、未対応時は説明付きで既存閲覧・相談へ戻れるようにする。

既存のメタデータ保存と文書・設問の対応構造を優先し、大量のテーブルや汎用状態マシンを新設しない。画面状態の所有元をViewModelに集約し、表示と操作イベントを分離する。本番DB移行が必要なら、具体的な差分・影響・復旧方法を示して別途確認する。

## 5. 実装する場合の順序と変更候補

1. **対象データの照合**: `portal_reader.py`、`collector.py`、`collection_store.py`。実データを読み取りで照合し、必要な抽出修正だけ確定する。設問表示情報と制約の扱いを決める。
2. **ES作業への入口**: `CareerCompanyScreen.kt`、`CareerNavigation.kt`、既存Navigationのentry登録、Career内のES作業画面。初期一覧から既存文書の閲覧までつなぐ。
3. **本文編集・保存・再開**: `CareerDialogs.kt`、文書表示部品、`CareerLocalStore.kt`、Career内の回答編集ViewModel、既存Repository、`api.py`、`shared.py`、`collection_store.py`。手動で1回答を保存・終了・再開する縦の導線を先に通す。
4. **設問を指定した相談**: `CareerCoachModels.kt`、Coach ViewModel/Panel、`coach_store.py`、`coach_runtime.py`、`coach_tools.py`。既存の募集会話と編集本文を接続し、AI案の保存と本人の採用・確認を分ける。
5. **1問の導線を受け入れ確認**: この募集の記述式1問について編集・相談・保存・戻る・再開と失敗系を通す。同時に全設問への到達、基本情報・選択・写真の表示、原順の確認経路が保たれていることを確かめる。依頼があるまで実装・端末更新・デプロイは開始しない。

順序は検証しやすくするためのもの。見た目の変更だけ、あるいは手動入力だけの段階をこの改修全体の完了とは扱わない。
