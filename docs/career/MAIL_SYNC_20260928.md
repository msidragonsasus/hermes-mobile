# 登録企業メールのサーバー同期

## 取得と保存

- 登録送信元を長さと件数で分割して検索する。検索ページは100件で、全ページを自動で再開する。受信箱全件の本文を読む方式ではない。
- アカウントの履歴位置を確保してから直近30日の検索範囲を固定する。直近分とそれ以前の取得位置を別々に保存し、新着の履歴確認を優先する。
- 新着確認は300秒間隔。無変更時はアカウントごとの profile / history の確認だけで、企業数に比例した検索をしない。処理遅延や取得制限がある場合は確認時刻・理由を表示する。
- `/collection/check`、定期処理、AI巡回前の更新は同じ永続要求番号を使う。プロセス間ロックにより重複取得を防ぐ。画面を閉じてもサーバーが継続する。
- 未保存IDのFromメタデータを確認してから本文を読む。アカウントとIDで本文を共有し、複数企業の関連付けは独立して保持する。
- 新しい送信元・企業への関連付けには、その範囲だけ初回取得を追加する。読み取りの間にも無効化・アカウント変更・送信元変更を確認する。
- 発見したIDはHTTP本文取得前に保存する。本文・証拠・企業への関連付け・処理位置の更新を同じトランザクションで確定し、部分失敗では未完了IDを残す。
- 履歴404は現在位置から差分を再開し、検索で登録送信元のIDを再照合する。検索ページ失効ではその検索を先頭から再開する。保存済み本文を再利用する。
- 初回・過去分は `initial_source` として保存し、通知対象外にする。新着は既存の通知分類と開始時刻で判定する。既存本文・証拠・関連付けを削除しない。

状態は既存SQLiteの `metadata` にアカウント単位で追加する。メール参照の上限には `career_mail_sequence` を追加し、既存の企業関連付けを一度だけ移行する。旧クライアントの取り込み成功はサーバー全体の同期成功時刻を更新しない。

## API・スマホ・AI

`GET /collection/mail-status` は保存済み状態だけを返す。Gmail呼び出しは行わない。`status` の主な項目は次のとおり。

| 項目 | 意味 |
| --- | --- |
| `recent_complete` | 登録送信元の直近分を取得し終えたか |
| `synced_through_at` | 最後に完了した差分確認の開始時刻 |
| `fresh` | 直近分が完了し、未完了の更新要求やエラーがなく、差分確認が300秒以内か |
| `backfill_complete` / `backfill_groups_*` | 過去分の完了と検索グループ数。推定メール総数ではない |
| `reason` / `retry_at` | 未確認理由と再試行予定 |
| `completed_generation` / `requested_generation` | 更新要求の完了範囲 |

スマホはメール設定の「自動同期」「全企業を更新」と保存状態を表示する。企業メール画面は保存済みメールを読み、更新ボタンも全企業の同じキューを使う。状態確認は画面表示中に5秒ごと、企業詳細の更新も保存データだけを読む。端末アクセストークンをサーバーへ転送しない。

AIの daily / research は実行前に差分同期を要求し、最大60秒待つ。失敗・時間切れでは最終確認時刻、範囲、`refresh_issue` を付けて保存データで続行する。未確認を「新着なし」と扱わない。

`career_context` は最初にメール関連付けの参照上限を固定する。受信日時順で最初の20件を渡し、`mail_next_cursor` の続きは次の引数で取得する。

```json
{"mail_company_id":"対象企業ID","mail_cursor":"前回のnext_cursor","mail_limit":20}
```

ページ上限は100件。作業対象外の企業は拒否する。後から取得されたメールを同じ巡回へ混入させず、企業のメール証拠も同じ上限に揃える。

## 測定と負荷制御

公開実装 [Nango Gmail同期](https://github.com/NangoHQ/integration-templates/blob/main/integrations/google-mail/syncs/threads.ts) の履歴・再開位置の扱いを確認し、[Googleの同期方式](https://developers.google.com/workspace/gmail/api/guides/sync) に沿って既存の公式Pythonクライアントを再利用する。別の同期サービスやOAuthクライアントを導入しない。

`tools/benchmark_mail.py` は本番DBをSQLite読み取り専用で開き、登録送信元の直近メール40件を限定サンプルとする。本文・件名・メールID・認証情報をログへ出さない。GmailとDBへの書き込みは行わない。既存認証の通常のトークン更新はWorkspace側に任せる。

- バッチ件数1→2→5→10→20→40、続いて並列リクエスト数2を試す。内側の同時要求は40以内。各並列レーンが独立したHTTPクライアントを持つ。
- v3以降は固定40通の先頭から各設定の1ステップ分（バッチ件数×並列数）で段階確認する。有力設定は同じ40通すべてで3回確認する。段階確認や途中終了を3回の確認に数えない。件数/秒、処理時間、最大ステップ時間、要求数、エラー率、再試行率、バッチHTTP応答のバイト数を記録する。バイト数は復号・展開後の応答本文で、ヘッダー/TLS/profile/listの通信量を含まない。
- 取得制限では増加を止め、Retry-Afterを守る。3回正常終了し、検証した中央値の最高速度の90%以上を出す最も負荷の低い設定を選ぶ。成功範囲をGmailの限界とは断定しない。
- v4は待機を含む30分・2,000要求・100MiBを目安に測定を打ち切る。各HTTP子処理は25秒・出力8MiB以内。各測定の内側では失敗を自動再試行で隠さず、その回を失敗として残す。v4は取得制限後に60→120→240秒と待機を延ばし、バッチ数・毎秒要求数を下げて別の測定を開始する。ヘッダー・エラー文中の再試行時刻・RetryInfoに長い待機指定があれば優先する。日次制限が明示された場合は測定を停止する。時間・要求数の予算終了は `stop_code` に分け、Gmailのエラー率には含めない。要求数は接続確認のprofileと進行中の取得も含め、次のステップの最大要求数を確保してから送信する。
- 運用時は未測定なら1件・並列1・毎秒1要求から開始する。件数・並列数に加え、測定済みの毎秒要求数も上限として保存する。取得制限や失敗ではバッチ数と毎秒要求数を減らし、指数バックオフとRetry-Afterを適用する。正常処理が続いたら検証済み範囲内で回復する。バッチも内側の要求数として数え、頻度は測定した上限を超えない（設定可能範囲は毎秒0.25～4要求）。制限解除時もこの上限を守り、再試行時刻はエラー受信時から計算する。

`tools/apply_mail_tuning.py --data-dir <既存DBディレクトリ> --report <測定JSON>` は3回の測定結果から選択を再計算し、対象アカウントが現在の設定と一致する場合だけ保存する。本番への設定適用はリリース作業時に行う。

認証・権限不足の403、取得制限の403/429、日次制限、通信障害は別のコードにする。[Googleのエラー処理](https://developers.google.com/workspace/gmail/api/guides/handle-errors) に従い、取得制限を再認証要求と取り違えない。

v3は小さい件数で40通を繰り返す予備測定を止め、短い段階確認と同じ40通での本確認に分けた。[Google公式クライアントのバッチ処理](https://googleapis.github.io/google-api-python-client/docs/batch.html) を引き続き使い、[Gmailの内側要求数の扱い](https://developers.google.com/workspace/gmail/api/guides/batch) に合わせて要求数の予算を確認する。新たな認証情報は不要。

v3の実測では、1・2・5・10・20件の短い段階確認は成功したが、40件設定で1通、続く20件設定の本確認で2通に `mail_rate_limited` が発生した。合計248要求。20件も3回確認には至っておらず、設定は未採用。v3のログはHTTP番号と制限種別を省いていたため、同時実行制限・分あたりの割当・日次制限のどれかは断定できない。

v4はこの失敗記録を入力し、既知の失敗より小さい10件以下・並列1・毎秒1要求から再開する。過去の異なるサンプルの速度は採用判定へ混ぜず、改めて同じ40通で3回確認する。確認中の再発でも自動で件数・頻度を下げ、上限まで再び増やさない。HTTP番号と固定分類（concurrent / bandwidth / daily / rate / unknown）のみ診断へ残す。エラー文の原文・メール本文・認証情報は出さない。

```sh
sudo -u hermes env PYTHONDONTWRITEBYTECODE=1 /var/lib/hermes/career-google-2.194.0/bin/python /tmp/hermes-mail-benchmark-20260928-v4/tools/benchmark_mail.py --resume-report /tmp/hermes-mail-benchmark-20260928-v4/prior-result.json --progress | tee /home/keiya/mail-benchmark-20260928-v4.json
```

進捗と待機は標準エラーへ、最終JSONだけを標準出力へ出すため、teeの保存先はそのまま設定確認に使える。v4は合成データで日次制限時の即時停止、制限後の別認証経路への切り替え停止、繰り返し制限での自動減速、異なる頻度や途中結果を3回確認へ混ぜないこと、運用時の測定頻度上限、エラー受信時を基準にした再試行を検証した。実アカウントでのv4測定は完了し、ユーザー提供の最終JSONから採用設定を再計算した。

## 「1日2万回」と割当の切り分け

[Apps Scriptの公式割当表](https://developers.google.com/apps-script/guides/services/quotas) にある個人アカウントのメール読み書き20,000/日は、Apps Scriptサービスの枠。今回の経路は公式PythonクライアントからGmail APIへ直接アクセスするもので、Apps Scriptは使用していない。ただしGoogle Cloudプロジェクトで別途設定された個別の上限は未確認。

[現在のGmail API割当表](https://developers.google.com/workspace/gmail/api/reference/quota) は、プロジェクト全体と利用者ごとの分あたりの割当単位を定めている。2026年5月の変更前に利用していたプロジェクトは従来の割当を維持するため、資料の値をこのプロジェクトの実設定とは断定しない。v4には現行公表値（profile=1、list=5、message.get=20）による単位数の推計を追加した。これは呼び出し回数とは別で、他クライアントの使用量やプロジェクトの実際の消費・残量を示す値ではない。

測定版は一時ディレクトリを使う（再起動などで消える場合は再配置する）。本番サーバーのコード・設定は2026-09-28に反映済み。端末アプリは今回更新していない。取得設定は上記の実測値を上限とする。

反映時は既存のリリース手順でDB・認証・設定をバックアップする。コードのみの許可リストとSHA-256を確認し、既存DBへ追加移行する。DB整合性・本文件数・企業関連付け・証拠件数を確認後、初回取得、5分後の新着、プロセス再起動後の再開、UI/AIの時刻表示を確認する。保存先を作り直したり、メールや証拠を削除したりしない。
