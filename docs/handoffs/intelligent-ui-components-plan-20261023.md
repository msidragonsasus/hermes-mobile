# Hermes 対話画面の部品方式への移行計画

2026年10月23日。計画段階。実装とサーバー反映はこの作業に含めない。

後続の実装依頼による初期カタログの結果は、[実装記録](intelligent-ui-components-implementation-20261023.md)を参照。計画時の方針と、配布・反映の実績を区別する。

毎回HTML・CSS・JavaScriptを生成する方式から、アプリが持つ部品へモデルがデータと設定を渡す方式へ移行する。目的は、トークン使用量と表示までの時間を減らし、操作性・視認性・計算の品質をアプリ側で保証できる範囲を増やすこと。既存のHTML回答と画像表示を維持する。

## 現状と再利用する実装

- `ui/chat/RichAnswerPrompt.kt` は毎回の送信に表示指示とスタイルガイドを付加する。`server/mobile_display` にもsystem sectionとpre_llm_call hookがある。指示の重複、継続ターンへの残り方、履歴再投入を含めて測る。
- `ui/chat/MarkdownText.kt` は閉じたhermes-uiブロックを認識し、`IntelligentUiDocument.kt` と `IntelligentUiCard.kt` が隔離WebViewを構成する。現在の逐次表示はブロック単位。
- `miniapp/sdui` には型付きJSON・検証・Compose描画がある。ただしcareer.mypageのID、権限、操作、APIと結び付く。検証パターンや汎用表示を再利用し、就活用の契約や権限をチャットへ持ち込まない。
- 単一の`:app`、既存のテーマ・画像取得・通常チャット送信・履歴管理を使う。見た目は既存トークンを共有しながら、対話UIでは読みやすさと入力の発見しやすさを優先する。ユーザーはこの面にMaterial Designの厳密な再現を求めていない。

## 公開実装の候補と採用判断

第一候補はAndroidX A2UI。任意コードを実行せず、モデルのUI記述をComposeへ描画する公式実装で、独自カタログにも対応する。2026年10月23日時点でengine/modelは1.0.0-alpha02。alphaのため、対応プロトコル・カスタム部品・逐次更新・依存関係を実際に組み合わせてから採用を確定する。[AndroidXリリース](https://developer.android.com/jetpack/androidx/releases/a2ui)、[描画とカスタムカタログ](https://developer.android.com/develop/ui/compose/agentic/render-surfaces)

[A2UI](https://github.com/a2ui-project/a2ui) は公開プロトコルとカタログの候補。同日の公開説明では0.9.1がproduction release、1.0はrelease candidate。AndroidXのライブラリ版とプロトコル版は別物として対応表を固定する。最新仕様へ無条件に追随しない。

[DivKit](https://github.com/divkit/divkit) もAndroid向けJSON描画の比較候補とする。PoCでジェスチャー、アクセシビリティ、Compose統合、APKサイズ、依存関係、ライセンスを確認する。A2UIが成立すれば並行導入しない。どちらも合わない場合に限り、既存SDUIの検証パターンを使う小さな型付きカタログへ切り替える。

## 構成

モデルが出すのは「部品ID・ラベル・初期値・データ・許可済み計算ID」。Androidが型と範囲を検証し、ネイティブ部品を組み立て、ローカル状態の変更から計算とグラフを更新する。HTML、CSS、JavaScript、任意コードによる計算式は新方式の契約に含めない。

部品は二段階にする。

| 層 | 初期範囲 | トークンを減らす方法 |
| --- | --- | --- |
| 組み合わせ済み部品 | 積立計算、比較表、系列グラフ | よく使う構成・計算・ラベル配置を実装済みにし、必要な設定だけ生成させる |
| 基本部品 | 見出し、本文、数値、スライダー、選択、切替、ボタン、表、折れ線・棒グラフ、詳細説明 | 組み合わせ済み部品で足りない場合にのみ、カタログの範囲で構成する |

独自の短縮記法とA2UIを混同しない。短いテンプレート指定を設ける場合はHermesのversion付きenvelopeと定義し、アプリ内でカタログへ展開する。モデルに短い指定と展開後のA2UIの両方を出させない。キー名の極端な短縮は、誤生成や修正ターンが増えないか測って判断する。

## 段階と合格条件

| 段階 | 作業と成果物 | 合格条件 |
| --- | --- | --- |
| 0 現方式の測定 | 積立、比較、グラフ、フォーム、図解の固定課題を用意し、現在のHTML・指示・再生成を測る。仕様・初期値・説明量を揃える | 出力、入力指示、継続ターン、最初の操作可能表示までの時間を分けた基準表がある |
| 1 描画方式のPoC | AndroidX A2UIでスライダー・数値・グラフの小さなサンプルを作る。カスタムカタログ、ライセンス、依存バージョンを検証 | プロトコル版を固定でき、文字拡大と通常チャット配下で連続ドラッグが動く。実測APK増分を説明できる |
| 2 積立計算を縦に完成 | 設定の受信から検証、描画、月末積立計算、グラフ、リセットまで接続 | 同じ設定の期待値と一致し、指を保持したまま値とグラフが更新される。元本上限、利回り0・負、積立0を確認 |
| 3 逐次表示と状態保持 | メッセージ単位で解析・適用し、本文と部品を混在表示。保存回答の再表示にも対応 | 回答の終了前に完成済み部品が使える。切断・再接続・REST再読込で二重表示や入力値の巻き戻りがない |
| 4 エージェントへ能力を通知 | 表示指示をversion付きカタログの短い案内へ整理。対応端末だけ新方式を生成 | 新旧端末・既存会話で正しい方式を選べる。通常チャット、画像、slash command、権限に回帰がない |
| 5 操作結果の共有と配布 | 明示操作で選択中の条件を次の通常チャットへ渡す。固定課題で削減率と操作性能を再測定 | 下記の受入条件を満たし、候補APKと必要なサーバーパッチを別々に検証してから配布する |

依存順は0→1→2→3→4→5。最初の配布範囲は積立計算、比較表、グラフまで。フォームと図解は、その後に使用頻度と削減効果を見て追加する。

## 逐次表示の契約

回答全体をひとつの巨大JSONにしない。既存テキストストリーム上で、version付きのUI領域から完結した更新メッセージを順に取り出す方式をPoCする。具体的なコードフェンス名やJSON形式は、A2UIとの対応確認後に確定する。新しいサーバーイベントが必要なら、それを別の変更として明示する。

- 途中まで届いたJSONはバッファに保持し、構文と部品の検証を通過したメッセージだけ反映する。分割されたUnicode・引用符・改行も扱う。
- データや子部品が未着の表示はプレースホルダーにする。計算に必要な条件が揃うまでは結果を確定表示しない。
- 表示の単位を安定したsurface/component IDで管理する。会話・ターン・メッセージの対応はホストが結び付け、モデル由来IDだけで別の回答を更新できないようにする。
- ストリームが累積本文の再解析になっても、同じ更新を二度適用しない。WS終端・REST再取得・メッセージID変更を含めて調停する。
- ユーザーが変更した値は、後から来たモデルの初期値で上書きしない。会話切替・再接続・再入場・アプリ再起動の保持方針を定義し、必要なローカル保存は既存DBを壊さない移行で追加する。
- 異常なメッセージでは最後に検証できた表示と入力値を残す。途中断絶は未完成と示し、HTMLへの自動変換や再生成を勝手に要求しない。

## ローカル計算と操作

初期の積立部品は、検証済みの月次積立計算を使う。開始資産、月額、年数、利回り、積立上限、積立タイミングなどを型付き設定にする。NISAの制度名・税率・枠をUI基盤へ固定せず、表示するシナリオの明示的な前提として扱う。条件と単位と丸め方を画面にも残す。

最初から汎用の式言語は作らない。計算の追加は許可済み計算IDを増やす方法とし、必要性が出た時点で処理量制限付きの演算グラフを検討する。グラフはローカル計算結果から描き、モデルに全月の値を列挙させない。

指の移動は端末内の状態更新だけで処理する。各フレームでネットワークやLLMを呼ばず、表示更新はフレームに合わせ、履歴を開く横スワイプと縦スクロールが干渉しないようにする。TalkBack、キーボード、拡大文字でも同じ部品を操作できるようにする。

エージェントへの共有は「この条件で相談」などの明示操作で、現在値と必要な計算結果だけを通常送信経路へ渡す。全ドラッグイベントやHTML全体は送らない。スナップショットは会話とsurface revisionを結び付ける。値はユーザー入力として扱い、権限やツール実行指示にはしない。未確定送信の自動再送は既存のUnknown送信ルールに従い禁止する。

## トークン削減の測定

減らす対象は生成コードだけではない。現在のクライアントsuffix、サーバーsystem section、継続ターンhookを追跡し、同じカタログ説明を何度も渡さない設計にする。カタログ本体は端末へ同梱し、モデルには対応versionと使う範囲の短い仕様を渡す。IDだけ渡してモデルが未知の仕様を理解すると仮定しない。

| 指標 | 測り方 |
| --- | --- |
| 出力トークン | 同一課題のUI出力と説明を、モデルに対応する同じtokenizerで比較する。文字数をトークン数と呼ばない |
| 総入力トークン | 共通履歴を固定し、表示指示・カタログ・後続会話・失敗時の修正分を加算する |
| キャッシュ | 使用可能ならcached/uncachedを分ける。文脈量の削減と料金の削減を区別する |
| 生成待ち時間 | 生成開始から最初の有用な表示、最初に操作可能になる時点、全体完了を別々に測る |
| 体感と性能 | ドラッグ中の反映遅延とフレーム時間、文字拡大時の操作到達性を測る |

積立計算・比較・グラフで、UI出力トークンの中央値50%以上削減を最初の目標に置く。これは実測前の目標であり、保証値ではない。指示込みの総トークンが増える構成は採用しない。大きな表や独自図解では削減幅が小さくなる可能性を課題別に示す。

ローカルfixtureとtokenizerによる比較から始める。実モデルの使用量は、既存の利用可能な経路で検証する段階に分ける。計測のために有料APIや別モデルを新規導入しない。必要なtokenizerがない段階はbytes/charsの参考値として表示し、トークン削減率は未測定とする。

## 移行と配布

旧hermes-uiのWebViewは保存済み回答用に残す。旧HTMLを自動で新方式へ変換しない。新方式の仕様が不明なクライアントには、本文・表など読める代替を返す。非対応versionや未知部品を実行せず、通常本文と画像は表示を続ける。

能力通知はversion、カタログID、利用できる計算・画像・状態共有の範囲を示す。クライアントが新方式を読める状態を先に用意し、その後サーバーの生成指示を対応能力に応じて切り替える。現在のhas_mobile_contextは旧preambleに依存するため、短い通知の導入時に新旧双方を試験する。画面の自己申告をツール実行権限に使わない。

APK、サーバー指示、実機、実モデルの証拠を分けて配布する。問題時は新方式の生成指示を止めても、既に保存された新方式回答は読めるようにする。アプリID・署名・設定・会話DBを保持する。サーバー反映が必要になった場合のHermesへの連絡は、従来どおりSlack #hermes-broを使う。

## 最終受入条件

- 代表課題ごとにトークン・表示時間・失敗修正分を比較し、出力50%以上削減の目標達否と総量を示す。
- 指を離す前に数値とグラフが複数回更新され、表示遅延p95を100ms以内にする目標で実測する。端末条件も記録し、60fpsを未測定で保証しない。
- 回答終了前に利用可能になり、後続更新・WS再接続・REST再読込で操作中の値を失わない。
- 狭い画面、明暗テーマ、文字1.5倍、TalkBackでも操作対象へ到達できる。
- 旧回答、通常本文、画像、履歴の横スワイプ、外側の縦スクロールに回帰がない。
- 新方式は任意JS・任意式・外部通信・ファイルアクセス・汎用native bridgeを追加しない。
- 構文破損、未知version/部品、重複ID、過大サイズ・深さ・系列数、非有限数、循環参照、切断途中を検証する。
- 送信・操作共有は既存の認証・承認・Unknown送信の扱いを守る。

実装の最初の着手点は、既存の積立fixtureを同条件の部品方式へ置き換える比較PoCとする。以後の採否は、その動作と実測値で決める。
