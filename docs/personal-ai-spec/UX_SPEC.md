# UX Specification

既存Compose / Material 3と [DESIGN.md](../../DESIGN.md) を継承する。
以下には目標UXも含まれ、共通カード・通知の完成を示さない。PR分割と未対応の扱いは
[実装計画](../personal-ai/IMPLEMENTATION_PLAN.md) に従う。

## 1. UX原則

### 1. Conversation is not the product

会話からすぐ相談・依頼でき、必要なときに「今やるべきこと」「AIが何をしているか」「人間が決めること」を確認できる。
就活Appは「ホーム／企業／相談／資料」の4領域へ分ける。初回はホーム、再訪時は同じ接続先・プロファイルの前回領域を開く（2026-09-19の承認済み再設計）。企業詳細は概要／募集・締切／メール／選考／メモの5タブとAI相談への入口を持つ。「応募管理」の独立画面と「記録」の分類は使わない。応募状態は募集単位で保持し、企業一覧のフィルタ・選考・就活ホームから確認する。

相談は企業・募集の関連付けを任意で持つ複数スレッドとする。同じ企業でもテーマごとに分け、会話名の変更・アーカイブ・復元ができる。本文と入力欄を主役にし、実行状態は上部バナー・詳細シート、モデル・provider・推論強度は入力欄付近の小さなボタンから開くシートに置く。複数スレッドによる実行の並列化は行わない。

資料は自己分析／ES／本人情報／経験。企業・資料のどちらからも同じESを開く。ESから相談へ進む際は設問・版・編集中の回答を端末に保持し、遷移だけでは送信しない。就活設定は右上の独立入口から開き、データ／AI／利用状態を見出しで区切った1本のリストに並べ（切替チップで隠さない）、企業設定は企業詳細から開く。詳細・会話・設定ではApp内4領域のタブを表示しない。

旧global・company:ID・offer:IDの本文・Run・IDは保持し、一覧用メタデータのみ追加する。旧サーバーでは従来会話へアクセスでき、新規スレッド作成には更新が必要と表示する。実装・移行・検証の詳細は[就活UI再設計の実装記録](../career/UI_REDESIGN_IMPLEMENTATION.md)を参照。

### 2. One input, many destinations

通常Chatと各Appの会話・下書き・実行権限は分離する。
通常Chatから就活Appへの自動ルーティングは行わず、Appsから利用するAppを選ぶ。

### 3. Progressive disclosure

最初は要点だけ見せる。
ツール引数、ログ、JSON、思考過程に相当する内部情報は必要時に展開する。
隠しすぎず、常時ノイズにもさせない。

### 4. Attention over activity

実行中の量より、人間の判断が必要な項目を優先表示する。

### 5. Safe by interaction design

危険操作は、単純な「OK」ではなく、対象・差分・影響を理解して承認できる形にする。

### 6. One-handed first

スマホ下部に主要操作を置き、片手で送信・承認・停止できる。

## 2. ナビゲーション

2026-10-05の依頼により、ChatをAgentへ統合し下部ナビゲーションを3項目にする。Agentの内容は既存Hermes Chatそのものを再利用する。
Appsボタンは、Apps選択中の再タップではApp選択画面へ戻る。別タブからAppsへ戻る場合は前回の内側画面を保持する。
Agentボタンは常に既存のHermes会話ルートを開く。明示的な戻る・閉じるとブラウザの安全な破棄は従来どおり。

```text
ホーム      Agent      Apps
```

ホーム / Agent / Appsの各ルート画面の右上にある設定アイコンから「アプリ管理」を開く。
先頭に横断検索と「設定」（アプリ設定・エージェント設定）を置き、続けて接続と認証、自動化、エージェントの機能、保存データ、診断・利用状況、開発者向けに分類し、用途を説明する。検索は画面名に加えてアプリ設定・エージェント設定の個々の項目も対象にする。

エージェント設定はサーバーconfigの全項目を並べず、人が変える項目だけを目的別の見出しと平易な言葉で示し、選んだ時点で保存して「元に戻す」を出す。アプリ側で選択肢とconfigキーを相互変換し、保存形式は変えない。危険側の選択（確認しない等）は確認ダイアログを挟む。全項目の編集は「詳細設定（上級者向け）」に残す。アプリ設定は外観・言語・チャット・動作を1画面に並べ、接続と「このアプリについて」だけを別画面にする。
詳細画面や各App内には共通管理アイコンを表示せず、画面固有の操作を優先する。
管理画面とその詳細では主要タブを表示せず、戻る操作で元の画面へ復帰する。元のタブのスタックは保持する。
2026-10-06の依頼により、Agent内Hermes会話の左上はチャット履歴を直接表示する。新規会話・検索・現在の会話の強調・追加読込を提供し、会話一覧画面は管理操作への補助導線として残す。履歴は既存の認証済みSessions APIを使用し、空・読込中・失敗と再試行を区別する。
Agent画面右上はラベル付きの「設定」から「この会話だけ」「Hermes全体の設定」「アプリ全体」を開く。会話モデルは会話内で変更し、接続先・プロファイル・スキル・ツール・動作設定は既存の管理画面へ移動する。ホームとAppsの共通管理入口は変更しない。
会話一覧もAgentの導線として扱い、管理ドロワーのスワイプは両画面自身で無効にする。
認証・初期設定を優先したうえで、同じ接続先・プロファイルの前回の安定した画面へ戻る。履歴がなければホームを開く。旧Today・Activityタブの保存先はホームへ移行する。
一時ダイアログ・認証画面・引数を伴う詳細画面は起動先に保存しない。

### 外部サービス連携

外部サービス連携（2026-10-24）: アプリ管理・アプリ設定に独立した入口を置く。
サービス一覧はアイコン、名前、短い日本語の用途、実際の接続状態で構成し、検索と
設定済み・要確認の絞り込みを提供する。詳細からアカウント管理・接続先設定へ進む。
Gmailの読み取り接続と、Calendar/Drive等の外部接続は区別する。MCP登録や有効化だけで
サービス認証済みとは表示しない。プラグイン画面からも同じ入口を開けるようにする。

### ホーム

2026-10-23の依頼により、主役を「今日やること」の一覧へ変更する。
メール・manaba等を確認し、行動・今日する理由・期限・元情報への入口を示す。
固定分類にせず、LLMが検索・読取・比較・優先順位の判断を行う。
取得した情報と前回の判断はキャッシュし、次回に再利用する。
今日必須／今日準備／要確認の順に整理する。未確認や部分取得を「やることなし」にしない。
完了チェックはこの一覧だけの記録で、メールの既読・課題提出・App内の対応完了とは別にする。
既存の「ホームに完了ボタンを置かない」は下記のApp提供項目に引き続き適用する。
前回情報は失敗時も保持し、日本時間で日付が変わったら古い一覧として表示する。
収集先を明示して有効にした場合、ホームを開いた日に一度確認する。
現時点の候補はGmail・manabaに対応し、他の情報源と朝定時の実行は未対応。
実装・接続条件は[今日やること](../../server/today_home/README.md)を参照。

既存のApp提供情報は、その下に表示する。
各Appが選別した「対応が必要」「届いた結果」を表示する。企業情報・通常の新着・収集判断は就活Appに保持する。
各欄は5件まで表示し、残りを展開する。承認・回答待ちは先頭、その他の対応は期限順、結果は新着順。
提供元・内容・期限・詳細への入口を表示し、巡回やツール実行のログは載せない。
結果は本文の表示成功で既読にする。既読と対応完了は別で、ホームに完了ボタンを置かない。
各Appのホーム表示設定は取得・OS通知と独立する。承認・回答待ちは常に到達可能にする。

### Agent内のHermes会話

新規依頼とセッション継続。

- 起動時は最後のセッションまたは空のComposer
- 上部のSession switcherで履歴へ移動
- モデル・推論強度は日常の操作として見える位置に置く。接続先・認証・プロファイルは管理設定で変更する
- 通常Chatと各Appでモデル・推論強度を別々に記憶する。既存Chatセッションの設定を優先する
- 就活の日次自動調査は手動会話と別のモデル・推論強度をサーバーに保存し、受付時に各Runへ固定する
- Tool eventsは本文の間にコンパクト表示
- 進行状況・中止・続行は依頼した会話内で扱う

### Agent選択

Agentには「会話／グループ」の切替を表示し、どちらも同じ基本の会話UIを使う。グループ専用の一覧・検索画面は設けず、左上の同じ履歴ドロワー内に「グループ名：会話タイトル」をセッション別に表示し、1タップでその会話を開く。
ヘッダーのメニュー・新規・設定、入力欄、ユーザーの吹き出し、Agent本文の表示部品を通常会話と共有する。参加者名・配信状態・グループ設定のみグループ固有の内容として扱う。
通常Hermes会話の履歴にも同じグループ会話を表示する。新規会話は＋から既存グループを選ぶだけで開始し、グループ作成も同じ入口に置く。
グループ名は作成時とグループ設定で変更でき、内部のグループ識別子・保存済み会話・下書きは維持する。
空のグループ画面には既存グループと参加者を表示し、タップするとグループ名と会話を切り替える。Agent発言はアイコン・送信者名・時刻と本文の面で区切る。グループ全体の進行と履歴はサーバーが所有し、画面離脱で停止しない。対応サーバーがない場合は更新を案内する。[サーバープラグインの実装・導入条件](../../server/group_chat/README.md)を参照。
会話へ戻ると切替元のHermesまたはOpenClawを表示する。
OpenClawはAgent名の選択から専用のネイティブ会話を開き、独立したGateway接続・認証・履歴を使う。
OpenClawの設定は専用会話右上、各Hermes botの既定モデル・推論強度は会話設定・bot編集・グループの参加bot設定から開く。
会話内のmodel／effortはその会話だけ、botの既定値は新しい個別会話・グループ会話に適用する。
接続先・端末承認が未確認のOpenClawを接続済みと表示しない。詳細は[OpenClaw統合](../agent/OPENCLAW_MOBILE.md)を参照。

Hermes会話の上部でエージェントを選ぶ。Hermesは既存Chat、会話履歴、接続先・プロファイル、モデル選択、通知ルートをそのまま使う。既存Chatの接続・オフライン・再接続・失敗状態を継承し、固定の接続済み表示に置き換えない。
broは未接続・利用不可として詳細説明を表示する。送信、承認、取消、自動接続は提供しない。別モデルをbroとして代用しない。
旧Chatルート、旧Agent一覧ルート、旧Hermes詳細は単一のHermes会話ルートへ統合する。保存済みCHAT設定はAGENTへ移行し、履歴や管理画面を保つ。bro詳細や未知のIDはHermesへ暗黙フォールバックしない。
引数付き詳細を永続起動先に保存しない。実装と残る接続条件は[Agent統合](../agent/AGENT_HUB_CANDIDATE.md)を参照。

### 実行イベント（診断）

従来のActivityはアプリ管理の「診断と利用状況 → 実行イベント」から開く。観測範囲と接続状態を示す。
従来の直接ルートは保持する。ホームには実行中セッション一覧を複製しない。

### Apps

Mini Appのランチャーと管理。
通常一覧は利用入口のあるAppを表示する。未稼働の同梱サンプルはアプリ管理の開発者向け画面から確認する。

サーバーターミナルは組込Native Appとして追加する。通常の入力欄で日本語入力・選択・貼り付けを行い、
明示的な送信でDashboardのシェルへ直接渡す。Enter追加の切替と特殊キーを入力欄の上に置く。
認証コードは秘密入力で扱い、AIの会話・端末の履歴DBへ渡さない。接続先・実行ユーザーとセッションの状態を示し、
接続断で入力を自動再送しない。出力選択、HTTPSリンクのブラウザ起動、文字サイズ、セッション再接続を提供する。
現行版にエージェント生成Appの動的追加runtimeはなく、この機能もAPKとサーバープラグイン双方の更新が必要。
導入条件と保持期限は[サーバーターミナル](../../server/mobile_terminal/README.md)を参照。

- Installed
- Available from server
- Disabled
- Search
- Permission review
- Update state

## 3. グローバルComposer

ホームとChatから常に開ける。

### 基本構成

```text
[＋] [何をする？                         ] [mic] [send]
```

`＋`:

- ファイル
- 写真
- カメラ
- URL
- クリップボード
- Mini App action

長押しや隠しジェスチャーを必須にしない。

### 送信前

通常は自動。

詳細シートでのみ変更可能:

- Destination / Mini App
- Session
- Model
- Background run
- Tool permission profile

### 送信後

- 即座にローカル表示
- server accepted / rejectedを後から反映
- 二重送信防止
- 送信状態が不明な場合は「確認中」とする
- 再送はserverのidempotency保証・scope・保持期間を検証できた経路だけで同一keyを使う。未対応では状態不明を保持し、WS request IDをidempotency keyとみなさない

## 4. ホーム画面詳細

- 就活Appは登録済みデータからルール判定し、追加のAI実行を行わない。
- 対象は応募・未完了タスクのある案件、志望度高/中または検討中の企業。終了・見送りは除外する。
- 締切は7日以内を表示し、時刻付きは48時間以内、日付のみは2日以内を強調する。日付に時刻を補完しない。
- 「対応が必要」の期限超過の未完了タスクは、日本時間の期限日から7日後まで残し、8日後以降は同欄から除外する。元データは削除・完了扱いにしない。期限なし・解釈不能は経過日数を推測せず残し、未確認・矛盾する期限を確定として表示しない（2026-10-05の表示方針）。
- 就活App内のホーム予定欄は、日本時間で前日以前の募集・締切・作業・予定を表示しない。「今日の締切・作業」は当日分のみとし、過去の記録は企業詳細に保持する（2026-10-02の表示方針）。
- 就活Appの「対応が必要」はメインホームと同じ既存Homeフィードのactionを表示する。会話以外の締切・メールも落とさず、期限超過7日以内の未完了の要対応は予定欄とは別に保持する。
- 選考結果の案内・予約・提出依頼・期限変更を、元の件名と出典で示す。合否の推測や一般告知の一括転送は行わない。
- 資料閲覧画面での「対応を終えた」はApp内の記録であり、実際の予約・提出ではない。読むだけでは対応済みにならない。
- 通常チャットは端末が受信した完了のみ対象。結果は保存先が判明した会話へ戻し、実際に回答が表示された時に既読にする。
- ホーム表示・復帰・手動更新と、表示中の60秒間隔で保存情報を読み直す。新しい巡回サービスは作らない。
- 失敗時は前回情報と確認時刻を保持し、未確認を空データとして表示しない。旧サーバーには更新が必要と表示する。

## 5. Chat画面詳細

### メッセージ表現

- User: 右寄せのコンパクトBubble
- Assistant: 全幅寄りのドキュメント型
- Tool: 折りたたみ式の構造化カード
- Approval/Clarification: 強調された操作カード
- Error: 再試行可能性と原因を分離

### ストリーミング

- ユーザーが下端にいる時だけ自動追従
- 上へスクロールしたら追従を停止
- 「最新へ」ボタンを表示
- token単位で毎回再描画せず、短い時間窓でまとめる
- Markdownの未完成構文で表示崩壊しない

### Tool card

折りたたみ時:

- tool名
- 実行状態
- 一行要約
- 経過時間

展開時:

- 入力要約
- 出力要約
- ファイル/差分
- ログ
- 再試行または関連Run

秘密情報はマスクする。

## 6. Approval UX

### 必須表示

- 何をするか
- 対象
- 外部への影響
- 可逆性
- 変更差分または要約
- 依頼元Run
- 有効期限
- 要求権限

### 操作

- Reject
- Modify
- Approve once

v1ではsession/always許可をUIとtransportの両方で禁止し、once/denyだけを許可する。
Modifyは安全に対応できる編集・再確認導線であり、専用endpointの存在を仮定しない。
未対応なら理由付きdisabled。編集だけで元要求を許可しない。
カードは元server/profile/session/request IDへ固定し、解決ACKまでRespondingを保持する。
要求失効・不明・接続先切替では返答を保留。期限が未提供なら不明と表示する。

### 高危険度

以下は追加確認または生体認証を検討。

- 公開投稿
- メール送信
- 予定の削除
- Git push / merge
- ファイルの広範削除
- 認証・秘密情報の変更
- 金融操作（初期版ではそもそも非対応）

## 7. Clarification UX

自由記述だけでなく、Hermes側が候補を返した場合は選択肢を表示する。

```text
どのリポジトリですか？

( ) personal-ai-shell
( ) batting-viewer
( ) investment-learning-memory
[別の名前を入力]
```

回答後、元のRunへ戻る。
新しいチャットを作らない。

## 8. 診断用の実行イベント

Runの状態遷移:

```text
Queued
  → Running
  → NeedsInput / WaitingApproval
  → Running
  → Completed / Failed / Canceled
```

表示上、`NeedsInput` と `WaitingApproval` は最優先。
Connection（Offline/Reconnecting等）はRun stateと別軸にする。切断時は最終確認時点を示し、
Unknown/再同期中をFailedへ変換しない。durable Run IDがないRPC経路は観測範囲を明示する。

### 詳細画面

- Run summary
- Timeline
- Active subagents
- Tool steps
- Artifacts
- Pending inputs
- Logs（折りたたみ）
- Stop / Steer / Follow-up / Resume

## 9. Apps UX

### カタログカード

通常のAppsランチャーは、64dpの角丸タイルに単色のシンプルなアイコンと名前を並べる。
アイコンと名前の領域をタップすると直接Appを開く。横長の説明カードや「開く」ボタンは置かない。
文字サイズに合わせて列数を調整し、名前の折り返しとスクロールを許可する。
以下の詳細情報は管理用カタログに適用する。

- アイコン
- 名前
- 目的
- 種別: Native / SDUI / Web
- Publisher
- Required permissions
- Version
- Enabled state

### 初回有効化

1. 機能説明
2. 要求権限
3. データ送信先
4. オフライン保存
5. 有効化

### 権限変更

## 10. オフラインUX

### 原則

2026-10-20のユーザー要望: 通常Chatの送信は、実行中・再接続待ちなら永続キューへ追加する。
元の接続先・プロファイル・会話を開き、明示的に送信待ちへ指定した同じ接続世代の間だけ、接続と実行終了を確認して一件ずつ自動送信する。再接続・アプリ再起動後は本文・添付・順序を保持した確認待ちの下書きとして表示し、本人が再度送信待ちに指定するまで送らない。同じ接続中の画面移動だけでは指定を失効させない。
キューは暗号化DBへ保存し、編集時は自動送信から外し、取消は送信前に行える。
実行中は「今の実行に追加」で明示的にsteerできる。`/queue`も同じキューを使う。
通常の下書きと送信結果不明な記録は自動送信しない。通知返信の下書きも従来通り。

理由:
時間依存・締切依存・外部状態依存の命令が古くなる可能性がある。

### 表示

- 明確なOffline banner
- キャッシュ済み履歴は閲覧可
- Composerの送信でキューへ保存し「キューに追加」と明示
- 再接続後は元の会話のidle確認後に順番に送信。状態不明なら待機
- 既存の下書きは「キューに追加 / 編集 / 破棄」を選べる

### 実行中に切断

- 「実行失敗」と断定しない
- `状態不明、再同期中`
- server Run IDがあれば照合。RPCでは元sessionのhistory/status/pendingと既存replayで再同期し、架空のRun IDを送らない

## 13. 視覚設計

### 基調

- 既存Jetpack Compose / Material 3、6 theme presetsとdynamic colorsを継承
- OLED friendly dark themeと既存light themeを維持
- 階層は色面と余白で表現し、影を多用しない
- statusはアイコン＋文言＋色
- コード/ログはmonospace
- UIに装飾目的の絵文字を使わない

### 情報密度

既存Hermes Mobileの高密度設計を維持しつつ、
日常画面では管理情報を減らす。
管理機能はアプリ管理（既存Advancedキー）へ退避し、既存画面・詳細導線を保持する。

### 共通部品とアクセシビリティ

Run/status、承認、質問、成果物はホーム/Chat/診断/Mini Appで共通部品を設計する。
HermesScaffold、StateViews、DetailDialog/Rows、既存Chat部品を再利用し、
semantic colors・LocalSpacing・既存Typography/Shapesを使う。画面単位の独自色/余白を増やさない。
Scaffold内はloading/error/emptyも同じinset ownerに従い、paddingValuesを二重適用しない。
日本語の折返し、文字拡大、TalkBackのラベル/状態/順序、48dp touch target、片手操作、
IME上の入力/承認/質問操作を確認する。承認の対象・影響を省略して密度を優先しない。
