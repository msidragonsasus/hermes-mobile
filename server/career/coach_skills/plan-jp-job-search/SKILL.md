# 応募ポートフォリオを設計する

単なる企業名の羅列ではなく、条件、選考時期、情報価値、準備負荷、内定の選択肢価値を比較する。

## 読むもの

現在の依頼に必要な参照だけ読む。本人事実を扱うときは証拠規約、対話では質問規約を確認する。状態に依存する最初の処理でstate-management、実際の接続・読書込でgithub-chat-storageを読む。state-patchは変更・復旧、移行資料とv3資料は該当作業時だけ読む。Pythonが使える場合の素材選択・再開確認には `scripts/coaching_state.py`、4.0読込には `scripts/migrate_state_v40.py` を使える。通常Chatでの実行を仮定しない。

`references/evidence-policy.md`、`references/question-policy.md`、`references/state-management.md`、`references/github-chat-storage.md`、`references/state-patch.md`、`references/web-research-policy.md`、`references/portfolio-framework.md`

## 手順

1. 既知の本人条件、理由付きdecision、現在の持ち駒、可処分時間を先に読む。依頼された選定範囲を定め、未確認で結論を変える条件だけ聞く。
2. 重要条件が不足し、候補群が大きく変わる場合だけ最大3問する。
3. 現在変わり得る募集、勤務地、処遇、インターンはWebで確認する。未確認情報を候補除外・推奨の確定根拠にしない。
4. 候補を、必須条件、本人接続、参入障壁・業務変化、配属リスク、選考難度、準備資産の共通性、情報価値、時間コストで比較する。
5. `挑戦 / 中核 / 安全網 / 探索` の役割を明示する。安全網を根拠なく断定しない。
6. 本人条件、準備負荷、情報価値から絞り、利用可能時間と締切で実行可能性を確認する。締切順だけで応募先を決めず、メール整理を勝手に始めない。
7. 各候補に推す理由、落とす条件、未確認事項、情報を得る方法を付ける。検討だけの依頼なら実行タスクの作成を強制しない。待遇等の本音と、仕事への関心仮説・応募文で説明できる接点を分ける。
8. 本人が選んだ企業候補、保留・不採用の理由と見直し条件を保存する。調査taskは必要な場合だけ作り、write-through同意があればSHA-safeに保存する。未保存なら`UNSAVED_JOBHUNT_PATCH_V4`を返す。Local v3互換時だけ従来patchを使う。
9. 内定取得後の承諾・辞退判断は応募前ランキングを流用せず、`compare-jp-job-offers` で実際のオファー条件から再評価する。

## 出力

今回の選定範囲に必要な比較・理由だけ示す。以下は内部の確認項目で、毎回すべてを見出しとして出さない。

1. **必須条件 / 希望条件 / 除外条件**
2. **応募ポートフォリオ**
3. **優先候補**（理由、懸念、信頼度）
4. **今は受けない候補**
5. **応募順と準備負荷**
6. **一週間の調査・応募タスク**
7. **未確認情報と出典**
8. **状態パッチのプレビュー / 未保存差分**

ランキングは本人条件に対する暫定順位として示す。未確認の年収、勤務地、優遇、締切を埋めない。
