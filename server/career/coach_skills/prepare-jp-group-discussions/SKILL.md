# グループディスカッションを準備・練習する

司会役の獲得を目的化せず、議論の品質と集団への実効的な貢献を練習する。

## 読むもの

現在の依頼に必要な参照だけ読む。本人事実を扱うときは証拠規約、対話では質問規約を確認する。状態に依存する最初の処理でstate-management、実際の接続・読書込でgithub-chat-storageを読む。state-patchは変更・復旧、移行資料とv3資料は該当作業時だけ読む。Pythonが使える場合の素材選択・再開確認には `scripts/coaching_state.py`、4.0読込には `scripts/migrate_state_v40.py` を使える。通常Chatでの実行を仮定しない。

`references/evidence-policy.md`、`references/question-policy.md`、`references/state-management.md`、`references/github-chat-storage.md`、`references/assessment-integrity.md`、`references/group-discussion-framework.md`

## モード

- **設計**: 形式、評価リスク、進め方、役割別の行動を整理する
- **個人ドリル**: 定義、論点、評価軸、要約、反対意見への応答を反復する
- **模擬GD**: 時間を区切り、参加者役と一問ずつ進める
- **デブリーフ**: 実施後の発言事実と改善仮説を記録する

## 手順

1. 企業・コース、人数、時間、オンライン／対面、資料有無、発表有無、既知のお題形式を確認する。評価基準を企業が公開していなければ断定しない。
2. 準備・模擬か、実施中の採点対象選考かを区別する。本番中の密かな発言供給、なり代わり、外部操作は行わない。
3. お題を、目的、対象、期間、制約、評価軸、必要情報へ分解する。定義を長引かせず、残り時間に応じて仮置きする。
4. 役割は司会、時間管理、書記に固定せず、論点提示、前提確認、他者意見の接続、反証、要約、収束、発表補助まで観測する。
5. 模擬では最初にお題と時間だけを提示し、ユーザーの初動を待つ。発言後に次の参加者反応や制約を出し、完成回答を先回りして渡さない。
6. フィードバックは、内容、構造、傾聴、巻き込み、修正、時間、収束、伝達へ分ける。一回の発言から性格や適性を確定しない。
7. 次回は改善点を最大2点に絞り、具体的な発言行動と観測方法へ変える。

## 出力

通常:
1. **形式とリスク**
2. **推奨プロセスと時間配分**
3. **役割別の貢献行動**
4. **今回の練習課題**
5. **評価と次回の改善点**

模擬GDでは、お題と制限時間だけを提示してユーザーの初動を待つ。
