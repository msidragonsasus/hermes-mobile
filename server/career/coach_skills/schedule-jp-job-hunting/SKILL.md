# 就活予定をカレンダーへ落とす

カレンダーの読取と書込を分け、書込は本人の明示依頼がある場合だけ行う。

## 読むもの

現在の依頼に必要な参照だけ読む。本人事実を扱うときは証拠規約、対話では質問規約を確認する。状態に依存する最初の処理でstate-management、実際の接続・読書込でgithub-chat-storageを読む。state-patchは変更・復旧、移行資料とv3資料は該当作業時だけ読む。Pythonが使える場合の素材選択・再開確認には `scripts/coaching_state.py`、4.0読込には `scripts/migrate_state_v40.py` を使える。通常Chatでの実行を仮定しない。

`references/question-policy.md`、`references/state-management.md`、`references/github-chat-storage.md`、`references/privacy-policy.md`、`references/calendar-policy.md`

## 手順

1. 予定化する対象、タイムゾーン、利用可能時間、固定予定、必要な準備時間を確認する。
2. カレンダーが利用可能で、本人が対象期間の確認を求めた場合だけ読む。予定作成の依頼を読取同意と推定しない。読取同意または本人が提示した対象期間の固定予定がない場合は、衝突未確認の下書きを示し、カレンダーへ作成しない。Hermes版ではHERMES.mdに従い、カレンダーへの外部書込は行わない。
3. 締切、イベント本番、準備タスクを分ける。締切だけを予定化して準備時間を消さない。
4. 締切の精度が `date_only` / `unknown` の場合、架空の時刻で登録せず、要確認または終日候補として明示する。
5. 重要度、依存関係、集中時間を考慮して準備ブロックを配置する。
6. カレンダー作成・更新は本人の明示依頼後に行う。招待者追加、既存予定の削除、辞退は別途明示が必要。
7. 実際に作成したイベントだけを作成済みと報告し、可能なら台帳へ参照を戻す。

## 出力

1. **予定化対象と前提**
2. **衝突・不足時間**
3. **推奨スケジュール**
4. **要確認の日時**
5. **実行したカレンダー変更**（実行時のみ）
6. **台帳へ戻す差分**

準備時間を詰め込みすぎず、実行可能性を優先する。
