# 選考後に学習する

単一の合否を人格評価へ変えず、観測可能な事実と検証可能な仮説へ分けて次回へつなぐ。

## 読むもの

現在の依頼に必要な参照だけ読む。本人事実を扱うときは証拠規約、対話では質問規約を確認する。状態に依存する最初の処理でstate-management、実際の接続・読書込でgithub-chat-storageを読む。state-patchは変更・復旧、移行資料とv3資料は該当作業時だけ読む。Pythonが使える場合の素材選択・再開確認には `scripts/coaching_state.py`、4.0読込には `scripts/migrate_state_v40.py` を使える。通常Chatでの実行を仮定しない。

`references/evidence-policy.md`、`references/question-policy.md`、`references/state-management.md`、`references/github-chat-storage.md`、`references/state-patch.md`、`references/learning-loop.md`

## 手順

1. 選考段階、日時、企業・職種・コース、質問・課題、本人の回答・行動、時間、直接フィードバック、結果を確認する。
2. 事実、解釈、感情を分ける。感情は尊重するが、原因の証拠にはしない。
3. 今回の観測をv4 `selection_events`の`EV-###`候補として構造化する。回答全文が不要なら要約し、第三者の個人情報を入れない。
4. 原因仮説を `HYP-###` として、支持事実、反証、代替説明、信頼度、次回の観測方法に分ける。
5. 単一の合否だけで、強み、弱み、企業適合、コミュニケーション能力を確定変更しない。
6. 過去イベントがあれば、複数回で再現した傾向と一回限りの事象を分ける。
7. 次回に観測できる改善実験を1〜3件へ絞る。変えることと変えないことに加え、観測指標、観測時点または対象、成功条件、反証条件を明示する。対象のHYP-###と再評価条件へ対応付け、次回の観測から支持・反証を判断できる形にする。
8. 選考観測と原因仮説を分ける。原因仮説は本人が採用・保存を望んだ場合にhypothesesのまま残し、write-through同意があればSHA-safeに保存する。一回の合否からprofile factを確定変更しない。
9. 保存不能時は観測・仮説を分離した`UNSAVED_JOBHUNT_PATCH_V4`を返す。Local v3互換時だけ従来のselection log/eventを使う。

## 出力

1. **CONFIRMED: 起きたこと**
2. **選考イベント候補**
3. **INFERRED: 原因仮説**（信頼度、反証）
4. **繰り返し傾向 / 一回限り**
5. **変えないこと**
6. **次回の改善実験**
7. **状態パッチのプレビュー / 適用結果**
8. **再評価条件**

合否を人格評価へ変換しない。
